# FoldReader 需求与设计说明书

**专为折叠屏手机打造的小说阅读器**

| 项目 | 内容 |
|---|---|
| 文档版本 | v1.2 |
| 适用产品 | FoldReader（com.llzx373.foldreader） |
| 目标平台 | Android（minSdk 33 / targetSdk 37），以大折叠 + 阔折叠为核心目标设备 |
| 初期格式 | TXT；后续扩展 EPUB / MOBI / PDF 等 |
| 技术栈 | Kotlin + Jetpack Compose + Material Design 3 Expressive |

---

## 1. 产品定位与目标

### 1.1 定位
市面上绝大多数阅读器是按"直板手机"思维设计的：屏幕变大了，只是把页面拉伸。FoldReader 的核心理念是——**折叠屏展开后不是"更大的手机"，而是"一本打开的书"**。铰链是书脊，左右两屏是左右两页。

### 1.2 产品目标
1. **折叠形态下尽善尽美**：折叠、展开、悬停（半折）、旋转、跨屏流转，每种姿态都有精心设计的阅读体验，而非简单拉伸。
2. **先把 TXT 做到极致**：大文件秒开、章节自动识别、排版精美、翻页流畅。
3. **架构为格式扩展而生**：解析层抽象为格式引擎接口，后期接入 EPUB 等格式时 UI 与阅读核心零改动。

### 1.3 非目标（本期不做）
- 在线书城 / 网络书源
- 账号体系与**云同步**（书签、划线标注均本地存储）
- 社交、评论、社区功能
- 扫描版 OCR（v2.1 起 PDF 文本型支持提取正文当电子书读，扫描件仍只做渲染与取字前的选词；
  见附录 v2.1 的已知取舍）

## 2. 目标用户与核心场景

### 2.1 目标用户
- **大折叠**手机用户（华为 Mate X 系列、三星 Galaxy Z Fold 系列、荣耀/OPPO/vivo/小米大折叠）
- **阔折叠**手机用户（如华为 Pura X 等 16:10 宽内屏新形态）
- 重度 TXT 网文/小说读者，本地藏书量大，对阅读体验敏感
- 直板手机与竖折 Flip 为兼容降级目标，不做专门设计

### 2.2 核心使用场景

| 场景 | 设备姿态 | 用户诉求 |
|---|---|---|
| 通勤碎片阅读 | 折叠态（外屏/合拢单屏） | 单手操作，与普通手机一致的阅读体验 |
| 居家沉浸阅读 | 完全展开（约 8 英寸，接近平板） | **双页书式排版**，像读纸质书 |
| 床头/桌面免手持 | 悬停半折（约 90°，立于桌面） | 上半屏阅读，下半屏控制/自动翻页 |
| 折叠/展开切换中 | 姿态动态变化 | 阅读位置、字号、设置**无缝连续**，不跳页不丢失进度 |
| 大折叠横持 | 展开 + 横屏 | 双页宽幅排版，充分利用宽度 |

## 3. 折叠屏形态分析（设计的物理基础）

### 3.1 设备形态抽象
通过 Jetpack WindowManager 获取 `FoldingFeature`，抽象出以下状态：

| 状态 | 判定条件 | 典型设备 |
|---|---|---|
| 折叠态（CLOSED） | 无折叠特征或折叠特征完全合拢 | 外屏使用 |
| 展开态（FLAT） | `state = FLAT` | 展开的大内屏（大折叠约 4:3 / 阔折叠约 16:10） |
| 悬停态（HALF_OPENED） | `state = HALF_OPENED` | 半折立于桌面 |
| 铰链方向 | `orientation = VERTICAL / HORIZONTAL` | 左右书脊 / 上下翻盖 |

**阔折叠适配要点**：阔折叠内屏为宽幅 16:10 左右比例（介于手机与平板之间），展开态**横持**时仍采用双页书式排版，但页宽较窄、行长取排版上限区间的下限；**竖持**（窗口高 > 宽）时左右并排会把每页压成窄条，自动模式退回单页（见 5.4）。其铰链方向（VERTICAL/HORIZONTAL）与展开比例需以运行时 `FoldingFeature` 实测为准，不写死任何尺寸。

**无铰链宽屏设备**：直板手机/平板横屏等无折叠特征但宽度达 EXPANDED 的设备，默认降级为单页；提供"宽屏双页"用户开关（默认关），开启后按屏幕中缝均分双页。

### 3.2 铰链（折痕）避让
展开态下，铰链区域（`FoldingFeature.bounds`）存在物理折痕，文字落在折痕上严重影响阅读。布局必须：
- 将屏幕按铰链区域划分为**两个安全显示区**；
- 正文内容严格避开铰链区域；
- 铰链本身作为"书脊"视觉元素融入设计（阴影、中缝），而非回避的缺陷。

### 3.3 姿态连续性（Continuity）
折叠/展开切换时（Activity 不重建或重建后恢复）：
- 阅读进度（精确到字符偏移）必须保持，目标页内容尽量延续；
- 双页 ↔ 单页切换时，以"当前左页首字符"为锚点重新分页；
- 字号、主题、亮度等设置即时生效，无闪烁。

## 4. 设计语言：Material Design 3 Expressive

整体 UI 遵循 **Material Design 3 Expressive** 最新设计标准（Compose material3 1.4+，以 `MaterialExpressiveTheme` 落地），而非基础版 M3。

### 4.1 主题与动效基调
- **主题入口**：`MaterialExpressiveTheme` + `MotionScheme.expressive()`，全 App 动画采用弹簧物理（spring physics），杜绝生硬线性动画；
- **色彩**：外壳 UI（书架、设置、对话框）启用动态取色（Android 12+ 壁纸取色）；**阅读区是例外**——阅读主题（护眼绿/羊皮纸/纯黑等）为沉浸阅读服务，独立于系统动态取色，但阅读控制面板、菜单等覆盖层仍遵循 M3 Expressive 组件规范；
- **字体**：采用 Expressive emphasized 字阶，标题更粗更有表现张力；正文阅读排版规则仍按第 5 章排版引擎要求执行；
- **形状**：加大圆角的 Expressive 形状系统，书架封面、卡片、底部面板统一应用。

### 4.2 组件选型（Expressive 新组件优先）
| 场景 | 组件 |
|---|---|
| 书架导航 | `NavigationSuiteScaffold`（折叠态底部导航 / 展开态侧边导航，随窗宽自适应） |
| 书架浏览 | 网格 + `Carousel` 封面浏览；大标题可折叠 TopAppBar |
| 导入入口 | `FloatingActionButtonMenu`（展开含"本地导入"等操作） |
| 解析/加载 | 波浪形 `LoadingIndicator` / `WavyProgressIndicator` |
| 阅读设置面板 | `ButtonGroup`、`SplitButton`、带刻度停靠的 `Slider`、分段按钮（翻页方式/主题选择） |
| 底部控制栏 | 悬停态下半屏控制面板、阅读菜单均以 Expressive 底部面板形态呈现 |
| 对话框/提示 | Expressive 规格的 AlertDialog、Snackbar |

### 4.3 与阅读体验的边界
阅读正文区追求"无 UI"沉浸感，Expressive 的表现力集中在**外壳 UI 与控件层**；正文区的翻页动画（覆盖滑动）手感与弹簧物理基调协调一致，但不套用组件动效。

## 5. 阅读界面设计（核心）

### 5.1 折叠态：单页模式
- 与常规手机阅读器一致：单栏正文、全屏沉浸、点击翻页/滑动翻页。
- 优化单手操作：翻页热区、底部控制栏布局按拇指可达区设计。
- 翻页方式只保留**覆盖滑动 / 无动画 / 上下滚动**三种，展开态与折叠态一致。
  仿真翻页（AGSL 铰链旋转 → 圆柱卷曲 → 紧圆角+斜面三版模型）已整体放弃：
  三版都没能达到与参考（微信读书录屏）一致的观感，核心症结是"翻起的那片纸"始终
  读起来像被挤出来的角/条，而不是一张摊平的纸；净收益压不过一整套额外状态
  （动画状态机、离屏位图缓存、掉帧降级、正/背纹理、透视与分层阴影）的维护成本，
  且已验证模型无法用简单调参收敛。完整实现保留在提交 `9a0c0ad`。

### 5.2 展开态：双页书式模式（标志性体验）
- 铰链左右各显示一页，合起来是"打开的一本书"：
  - **左屏 = 左页，右屏 = 右页**；翻页一次翻两页（书式语义）。
- 双页排版细节：
  - 左右页内侧（书脊侧）留白略大于外侧，模拟真实书籍装订；
  - 书脊中缝渲染柔和阴影渐变，增强立体感；
  - 页码、章节名分别置于左右页外侧页眉/页脚。
- 翻页动画：**覆盖滑动 / 无动画 / 上下滚动**三种（滚动模式下双页退化为双栏连续文本）；
  展开态与折叠态共用同一套方式，不再有仿真翻页分支。
- **竖持退回单页**：窗口高 > 宽时，左右并排的两页各窄成一条，双页书式在物理上不成立，
  自动模式一律单页（展开的阔折叠竖着拿即属此列）；窗口宽 ≥ 高（横持）才进入双页。
  确实想要竖持也双页的用户，可把双页模式设为"强制双页"。
- 用户可设置展开态强制单栏（宽幅单栏），满足不喜欢双页的用户。

### 5.3 悬停态：桌面模式（Tabletop）
- 上半屏：正文（单栏）；
- 下半屏：控制面板——
  - 翻页按钮、进度条/章节跳转；
  - 亮度、字号快捷调节；
  - **自动翻页**开关与速度（解放双手的"桌面阅读"场景）；
- 下半屏面板支持熄屏（屏幕下半变暗节能，AMOLED 友好）。

### 5.4 横竖屏
- 展开态横持：保持双页，页宽变宽，行长按排版舒适度上限（约 40 字符/行）约束，超出部分居中留白。横持时铰链相对窗口为水平方向，双页按屏幕中缝均分（左右等宽）。
- 展开态竖持：**单页**。竖屏下窗口高远大于宽，双页并排会让每页窄到无法成行；退单页后整幅宽度交给一页，
  行长仍按上限约束、超出部分居中留白。判定只看**真实窗口宽高**（`LocalConfiguration` 的
  `screenWidthDp` / `screenHeightDp`），与是否上报铰链无关——阔折叠竖持（无铰链或铰链不参与分割）
  同样退回单页。不能拿 `WindowSizeClass` 的 `minWidthDp` / `minHeightDp` 推断方向：那是断点下限。
- 折叠态横持：单栏宽幅，遵循同样的行长上限。
- 姿态连续：横竖切换与折叠/展开一样，以锚点重分页，单页 ↔ 双页无感切换。

### 5.5 排版引擎要求
- 行长上限：中文每行 18–40 字可调（默认随屏宽自适应）；
- 首行缩进 2 字符、段落间距、行距、字距可调；
- 标点避头尾、两端对齐（中文排版基本功）；
- 支持字体导入（TTF/OTF）与系统字体；
- 页边距、书脊间距可视化调节。

### 5.6 阅读辅助功能
| 功能 | 说明 |
|---|---|
| 目录 | TXT 章节自动识别（正则规则库："第X章/卷/回"等，可自定义规则） |
| 进度 | 百分比 + 章节进度 + 全书剩余时间估算 |
| 书签 | 任意位置加书签（锚点精确到字符偏移，同页可有多条），列表管理（按创建时间排序），双页模式下左右页可分别添加 |
| 划线标注 | 长按选择文本划线（多色）并可附笔记；标注列表按章节分组；标注锚定字符偏移，姿态切换/重排版后位置不变；本地存储，不依赖云同步 |
| 跳转 | 按百分比、按章节、按书签跳转 |
| 搜索 | 全文搜索，结果按章节分组 |
| 夜间模式 | 随系统 + 手动；纯黑 AMOLED 主题 |
| 主题 | 预设护眼绿/羊皮纸/灰白等 5+ 主题，支持自定义背景色与文字色 |
| 亮度 | 应用内独立亮度，下拉手势调节 |
| 自动翻页 | 按时间滚动/翻页，悬停态重点功能 |
| 翻页方式 | 覆盖/无动画/上下滚动，点击热区与音量键翻页可配 |
| 屏幕常亮 | 阅读界面保持唤醒（可关） |

## 6. 功能需求（非阅读界面）

### 6.1 书架
- 本地书架：封面（TXT 自动生成书脊式封面）、书名、进度、可选排序（按导入时间 / 按书名 / 按阅读进度，默认按导入时间）；
- 网格/列表两种视图；展开态下自适应多列；
- 批量管理：删除、分组（v1.1）。

### 6.2 TXT 导入与解析
- 来源（仅本地，不做 WiFi 传书 / 网络导入）：
  - 系统文件选择器（SAF）从书架主动导入；
  - **"打开方式"绑定**：注册 `VIEW` Intent（`text/plain`，`content` / `file` scheme），用户在其他 App（文件管理器、微信、邮件等）选择"用 FoldReader 打开"时直接导入并进入阅读；
  - 外部打开的书籍自动进入书架（同一文件 Uri 去重，重命名/移动后以内容哈希兜底识别）；
- 编码自动检测：UTF-8 / UTF-16 / **GBK / GB18030**（国内 TXT 重中之重）/ Big5；
- 大文件处理：
  - 100MB+ TXT 秒开：不整文件载入内存，按字节偏移**懒加载 + 滑动窗口缓存**；
  - 章节索引后台异步建立，建立期间可直接阅读；
- 智能清理选项：去空行、去广告行（正则替换规则，v1.1）、繁简转换（v1.1）。

### 6.3 阅读历史与进度
- 每本书记录：字符偏移进度、阅读时长、最后阅读时间；
- 打开书籍自动回到上次位置；
- 书签与划线标注随书籍记录，全部本地存储（Room），支持按章节浏览与跳转、编辑笔记、删除。

### 6.4 设置
- **每书偏好**（`book_prefs`）= 会随书独立演化的项：正文排版（字号/行距/边距/行长/段距/字距/字体/首行缩进）、主题配色、翻页方式、阅读器内菜单的项（亮度/自动翻页/桌面面板熄屏）、PDF 阅读模式、漫画的方向与适应模式。每本书首次打开时拷贝全局默认，之后独立演化；
- **全局偏好**（DataStore）= 其余一切，**不**进每书表（设置页改完立即对所有书生效）：双页模式、翻页热区比例、中间单击/双击、音量键翻页、手势开关、宽屏双页、规避摄像头、屏幕常亮、页眉页脚各显示项、封面单独成页、跨页大图识别、滚动页间距、书架与清洗规则等；
  *（判据：只有「这本书的正文怎么排」与「这本书的阅读模式」才该随书演化；交互开关与显示项是应用级偏好，做进每书表会让设置页对已打开的书失效。）*
- 翻页热区、音量键、手势自定义；
- 备份与恢复（书架数据、设置，本地导出，v1.1）。

| 兼容 | minSdk 33；直板手机全功能可用（折叠特性优雅降级） |

## 8. 技术架构设计

### 8.1 总体架构
单层 App 模块起步，包结构按**特性 + 分层**划分，遵循 MVVM + 单向数据流：

```
com.llzx373.foldreader
├── core/
│   ├── format/          # 格式引擎抽象（BookParser / BookContent / Chapter）
│   │   └── txt/         # TXT 实现：编码检测、章节切分、窗口化文本读取
│   ├── reader/          # 排版分页引擎（Paginator：文本 → 页列表）
│   ├── foldable/        # 折叠状态感知（FoldingState / Posture / 铰链区域）
│   └── data/            # Room（书架/进度/书签）+ DataStore（设置）
├── feature/
│   ├── bookshelf/       # 书架
│   ├── reader/          # 阅读器（单页/双页/悬停三态 UI + 手势 + 动画）
│   ├── importer/        # 书籍导入
│   └── settings/        # 设置
└── ui/theme/            # 主题
```

### 8.2 关键模块设计

**（1）格式引擎抽象（为后期扩展预留）**
```kotlin
interface BookParser {
    suspend fun parseMeta(uri: Uri): BookMeta
    suspend fun parseChapters(uri: Uri): List<Chapter>
    fun openContent(uri: Uri): BookContent   // 随机访问的文本源
}
interface BookContent {
    val charCount: Long
    suspend fun read(range: LongRange): String  // 按字符偏移窗口读取
}
```
后期 EPUB 只需新增 `core/format/epub` 实现同一接口。

**（2）TXT 窗口化读取**
- 文件按检测编码建立"字节偏移 → 字符偏移"映射索引（Room 持久化，按文件长度 + 内容哈希校验失效）；
- 索引后台增量建立，建立期间可直接阅读（读取仅等待所需数据块就绪，不阻塞全文索引）；
- 阅读时仅解码当前页 ± 若干页窗口，内存占用与文件大小解耦；
- **块解码缓存**：按（起始块, 结束块）缓存解码结果（容量 8 条），相邻段落与搜索上下文反复读同一块时不再重复 seek + 解码；解码器与字节缓冲按实例复用。

**（3）分页引擎 Paginator**
- 输入：文本窗口、页面尺寸（px）、排版参数（字号/行距/边距）；
- 输出：`List<Page>`（每页 = 字符区间 + 行布局）；
- 基于 `StaticLayout` 度量；页边界索引（每页字符区间）按（书籍 + 排版参数哈希 + 视口尺寸）磁盘持久化，行布局由内存 LRU 按需重度量；
- **行几何缓存**：逐行字宽与两端对齐字距按（页实例 + 全部几何参数）缓存（容量 32 条），
  绘制期不再逐字符 `measureText`；字宽用 `Paint.getTextWidths` 一次取整行；绘制用 Paint 按线程复用。
  键含页**实例身份**而非结构相等——内容变更后新建的 Page 必须重新度量。颜色不进键（换主题不失效）。
- **页边界索引追加式落盘**：后台全书分页每 64 页落盘一次，只追加新增尾部（首尾头部不变、
  先写数据后更条数，中途崩溃时仍自洽），不再每轮重写整份数组；
- **缓存生命周期**：删书时按 bookId 清理该书全部版式文件；启动后闲时 GC 掉孤儿文件，
  并对每本书按最后修改时间保留最近 4 份版式（改字号/行距/页宽各会生成一份）。
- 双页模式下左右页共用同一分页流，仅是相邻两页（单一 Paginator，页宽取左右安全区较小值）。

**（4）折叠感知 FoldableState**
- 以 `WindowInfoTracker` Flow 封装 `FoldingFeature`；
- 输出：`{ posture: CLOSED|FLAT|HALF_OPENED, hingeBounds: Rect?, hingeOrientation }`；
- 阅读界面以此为一级输入决定布局模式，配合 `calculateWindowSizeClass` 做宽度兜底。

**（5）状态连续性**
- 进度锚点 = 当前页首字符偏移（Long），与布局无关；
- 姿态变化 → 以锚点重新分页 → 定位到包含锚点的页，天然无丢失。

#### 8.4.1 系统栏 inset 与外壳导航组件（返回书架跳动的根因约束）

外壳用 `NavigationSuiteScaffold`：展开态（横屏内屏）为 `NavigationRail`，其在 start 侧的内边距
= `systemBars ∪ displayCutout` 的 start inset，**rail 宽度 = 80dp + start inset**，而页面内容被放在
rail 右侧（`contentPlaceable.placeRelative(railWidth, 0)`）。因此 start 侧系统栏 inset 的任何变化
都会把整页内容（网格封面、右上动作、FAB）整体水平推移。

阅读页沉浸（`hide(systemBars)`）会把四边 inset 归零；恢复（`show`）由系统异步派发，状态栏与
导航栏可能各自先后到位（横屏侧边导航栏常晚于状态栏）。若在 inset 未落地前就返回书架，书架首帧
按 start=0 布局、导航栏 inset 随后到达 → rail 变宽 → **封面与右上/右下按钮整体向右跳一次**
（竖屏三键导航则表现为向下跳）。

约束（改代码时必须保持）：
1. **外壳形态与路由无关**：阅读页不进出 content 槽，而是由 `ReaderOverlay`（`SharedTransitionLayout`
   内、`NavigationSuiteScaffold` 之外的全窗口覆盖层）渲染，NavHost 中只保留空占位目的地用于压栈/
   参数/返回语义。这样 rail 宽度只随系统栏 inset 变，书架退场不再重排，阅读页也不会先窄后宽重排。
2. 离开阅读页必须经 `leaveReader`：先 `BEHAVIOR_DEFAULT + show(systemBars)`，再由
   `BarsRestoreGate` 等**外壳 inset 快照（`systemBars ∪ displayCutout`）等于沉浸前实测快照**
   并连续两帧稳定，才导航（800ms 超时兜底：超时日志 `gate TIMEOUT` 意味着仍有跳动风险）。
   注意两个坑：只比 `systemBars` 会漏掉挖孔屏沉浸期才上报的 `displayCutout` 侧边 inset
   （真机实测 `show()` 后仍停留 ~500ms → 书架右边缘外扩 140px）；用
   `getInsetsIgnoringVisibility` 当期望值同样无效（`displayCutout` 不受显隐影响，会拿到沉浸期那一份）。
   参考值由 `ShellInsets` 在进阅读页与沉浸前记录。
3. 不要用 `NavigationSuiteScaffoldState.snapTo(Hidden/Visible)` 控制导航组件显隐——布局内部
   有按 state 驱动的 `animateFloatAsState` 占位动画，切换时会逐帧挤压内容；只用 `layoutType`。
4. 阅读页占位目的地的转场时长必须 ≥ 覆盖层退场动画（见 `readerPlaceholderEnter/Exit`）：
   NavHost 在转场跑完才把 entry 置为 `DESTROYED`，否则覆盖层会在 entry 销毁后继续组合，
   `viewModel()` 访问已销毁 entry 的 ViewModelStore 直接崩溃。
5. **离开阅读页后的短暂窗口要抑制"额外 inset"**：真机（Xiaomi 阔折叠内屏横屏）实测，平台在
   每次系统栏显隐（`hide`/`show`）之后都会补报一次挖孔侧边 inset（140px=50.9dp），约 500ms 后
   才消失，且出现时机比门控采样更晚——只靠门控无法避免"书架首帧按带瞬时 inset 的宽度布局、
   500ms 后右边缘外扩"。因此 `FoldReaderApp` 在外壳根节点用 `consumeWindowInsets(
   ExtraOverReferenceInsets(实时 ∪ inset, 沉浸前实测快照))` 把这份额外量消费掉（`max(0, 差)`，
   额外量归零后自动失效），只在刚离开阅读页的 1.2s 窗口启用。
6. 回归判定：`ReturnTrace`（debug）中 `shell: slot pos=...`（进书瞬间不变）与
   `bookshelf: content pos/size`（返回后恒定）都应保持稳定；`leaveReader gate frame#N shell=...`
   应与 `reader enter/immersive` 记录的 `reference=` 一致后才放行；`shell: suppressExtraInsets on/off`
   期间布局不应变化；并确认无 FATAL。

3. **数据与功能**：不做云同步，所有数据本地存储；书签与划线标注（含笔记）列入 v1.0 范围。

**已决议的产品决策（v1.2 增补）：**
4. **宽屏双页**：无铰链宽屏设备（直板/平板横屏）默认单页，"宽屏双页"开关可选开启（设置页）。

7. **横持双页**：展开态横持（铰链相对窗口为水平）保持双页，按屏幕中缝均分。
8. **规避摄像头位置**：双页模式可选开启（设置页，全局开关）：按 `WindowInsets.displayCutout`
   自动检测屏幕开孔位置——开孔压住右页顶部时，奇数序页（跨页右页）分页减容、顶端下移足够行数

   滚动/单页模式不适用，无开孔设备无效果。
9. **竖持单页**：自动模式下，双页要求窗口**宽 ≥ 高**（横持）。竖持（高 > 宽）时无论是否上报铰链、
   宽度是否达 EXPANDED，一律退回单页——两页并排会把每页压成窄条。用户显式选"强制双页"不受此限。

## 附录：v1.4 性能专项·第二批（滚动模式）

对标同上。核心问题：滚动时跨一页就更新一次位置，而位置字段与结构字段同处一个 `ReaderUiState`，

## 附录：v1.5 偏移索引的代理对跨块修复

**问题**：`TxtIndexer` 的输出缓冲只剩 1 个槽位、而下一个字符是需要 2 槽的增补字符
（emoji、CJK 扩展 B 等）时，会以「不足 blockChars」的块提交，块起点变成 4095 / 8190 / …
这类**非均匀序列**。

而 `offset_index` 表只持久化每块的字节偏移，恢复时由 `RoomOffsetIndexStore.buildSnapshot`
按 `i * blockChars` **重建**字符起点——两者不一致，于是：首开（内存索引，正确）与后续打开
（恢复索引，起点整体偏移 k）读出的文本不同；偏移随块号线性增长（第 k 块错 k 个字符），
靠后位置 `substring` 还会越界抛异常。

**为什么不能靠推算**：增补字符在 UTF-8 里是不可分割的 4 字节，字符块边界一旦落在它内部，
这个边界上就**不存在**合法字节偏移。所以「块起点是非均匀的」是数据模型的必然结果，
唯一的正解就是把真实字符起点也存下来。

**处理**（数据库 v12）：
- `offset_index` 改为双列模型：`charOffset` 更名 **`byteOffset`**，新增 **`charStart`**（块的真实字符起点）；
- `OffsetIndexBlock(chunkIndex, byteOffset, charStart)` 作为写入侧模型，
  live 索引路径逐块落盘时一并带上字符起点；
- `RoomOffsetIndexStore.buildSnapshot` 直接取存量起点，校验从「绝对位置落在 `((n-1)B, nB]`」
  改为**按相邻跨度**：字符/字节起点严格递增、每块字符跨度 ∈ `(0, blockChars]`、首块起点为 0、
  末块由 `totalChars` 收尾且跨度同样受限；
- `MIGRATION_11_12` 重建空表（旧行只有字节偏移，真实起点已丢失，搬过去也是错的）。

**顺带**：压平文件（EPUB/FB2）的章节来自 `.toc` sidecar，索引扫描期用章节正则扫出来的结果
本就被丢弃（`onChaptersIndexed` 为空回调）。现改为传空规则集，那次后台扫描只剩纯解码，
去掉了每行一次的正则匹配。

### 已评估并归档（不做）

以下都逐条评估过，结论是不值得做。完整理由与推翻条件见 `TODO.md` 的 M5.12。

- **EPUB/FB2 首开仍在首帧前整本压平**。v1.6 的导入后预热已把「首开等压平」压缩到
  「导入后立刻点开」与「预热失败后首次打开」两种少见情况；且尚无实测数据表明这一等待不可接受。
  *更正本附录早先的判断*：原记的「样式 span 必须等整本压平完才能定稿」过于悲观——
  粗体/斜体/上下标的 span 偏移是位置局部的，可随章节产出；只有内部链接解析、纸书页码、
  锚点表需要整本遍历。真正的实现门槛是「生长中文件的索引循环」。
- 「压平时顺带产出偏移索引」：v1.5 的双列模型已让这件事在技术上可行，
  但收益只是省掉首开后的一次后台全量解码（不挡首屏）。
- `preferredStartOffset` 在首开无进度时整本复制一次源文件：每本书至多走一次。
- 书架查询 `SELECT books.*`：收益是少读几个短文本列，代价是牵动书架 UI 全部取值点。
- `ScrollContent` 的函数引用（`::scrollCaretAt` 等）每次重组新建；
  该 Composable 的形参本就不稳定，单独稳定函数引用不会让它可跳过。

## 附录：v1.6 导入后后台预热 + 就绪角标（数据库 v13）

**动机**：EPUB/FB2 的整本压平原本只在首次打开时做，用户点开书要等（大书可达数秒）。
而导入本身是「写完库即返回」——等于把成本从"用户预期等待"的导入挪到了"用户预期瞬时"的打开。

**做法**：导入流程保持原样（不入队、不阻塞），成功后把这本书投进**后台预热队列**
（`BookPrewarmQueue`）：串行、每本之间让出、失败静默。等用户真去点开时，通常已经命中缓存。

- `BookParser.prewarm(uri)` 默认无操作；EPUB/FB2 实现为「压平 + 回填章节表」。
  TXT 不入队（它没有压平步骤，偏移索引在打开时边建边读）。
- 预热成功回写 `books.contentPreparedAt`；阅读器打开成功后也回写一次——
  预热失败或进程被杀时，这条是兜底。
- **同一 hash 的压平串行化**（`ConvertedBookStore.withFlattenLock`）：预热与阅读器可能同时
  发现缓存缺失（"导入后马上点开"就是这个时序），并发压同一本书会白做一遍，
  而那正是用户正在等首屏的时刻。拿到锁后必须再查一次缓存。

**就绪角标**：书架封面左下角显示「待解析」，`books.contentPreparedAt` 回写后随 Flow 自动消失。
判定规则收在 `BookEntity.needsContentPreparation()` 里 —— 只有 EPUB/FB2 且未就绪才提示。
记在数据库而不是每次去 stat `converted/`：一是角标要能随预热完成自动消失（文件系统没有变更信号），
二是书架 Flow 在阅读期间会被进度更新反复触发，逐本查文件不划算。

列表视图的封面只有 46dp 放不下角标，改在副标题下补一行「待解析」，信息一致。

## 附录：v1.7 目录（修复 + 层级展示，数据库 v14）

### 一、「没有目录」：章节回填失败后无法自愈

**现象**：某本 EPUB 打开后目录面板显示「未识别到章节」，但同一文件用解析器单独跑能出 26 章
（实测：`epubmerge` 合并型合集，根 OPF + 根 NCX，7 本单行本共 26 个 navPoint）。

**根因**是三个缺陷叠加，导致章节回填一旦失败就无法恢复：

1. 章节只在 `flattened.fresh`（本次**确实**压平了）时才经 `onChaptersIndexed` 落库；
2. 这次调用被 `runCatching` 包着，**写库失败被静默吞掉**，没有任何痕迹；
3. 阅读器里那条兜底（章节表为空就重扫一遍）在**实时索引**期间直接 `return` ——
   而首次打开必然是实时索引。

于是失败后的第一次打开不会自愈，用户看到的就是「没有目录」。

**处理**：

- 兜底补扫的判定抽成 `shouldScanChaptersInBackground(liveIndexing, cheapChapterScan)`：
  只对 **TXT** 在实时索引期间跳过（它的 `parseChapters` 是一次全量索引扫描，贵）；
  **EPUB/FB2 照常兜底**（它们的 `parseChapters` 只读压平产物旁的 `.toc` sidecar，很便宜）。
  这样「没有目录」在**本次打开内**就能自愈。
- 补扫与补写失败都写进 `DiagnosticLog`，不再静默。

### 二、目录层级被拍平

合并型合集的目录天然是两级的：一级 navPoint 装书名，二级装章节。
原先 `parseNcx` / `parseNav` 把嵌套**拍成一层**，于是 26 条条目平铺在一起，
书名和章节名分不清主次。

**处理**（数据库 v14）：

- `EpubStructure.TocEntry` 与 `Chapter` 增加 `depth`（0 为顶层）；
  NCX 按 `navPoint` 嵌套深度、NAV 按 `<ol>` 嵌套深度计算；
- `chapters` 表新增 `depth` 列（`ALTER TABLE ... NOT NULL DEFAULT 0`，
  已有数据保留 —— 丢了 TXT 就得全量重扫）；
- 目录面板按 `depth` 缩进（步长 14dp，封顶 4 级）。

层级只影响**展示**：跳转、进度、书签锚点始终是字符偏移，与层级无关。

**Compose 稳定性**：本项目走 AGP 9 内置 Kotlin 编译，实测 `composeCompiler {}` 的
`stabilityConfigurationFile` / `metricsDestination` 不会接到编译任务上（改配置文件不会让
`compileDebugKotlin` 失效，指标目录也不生成）。稳定性一律用代码里的 `@Immutable` / `@Stable` 声明。

## 附录：v1.9 竖持退回单页

**现象**：真机（阔折叠）展开后竖着拿，阅读页仍是左右双页，每页窄到无法成行。

**根因**：`resolvePageLayoutMode` 的双页判定只看姿态与宽度类别，**完全不看窗口方向**：

- `FLAT && 铰链存在 → 双页`：阔折叠多为上下折，展开时上报水平铰链，于是竖持照样判双页
  （实测设备命中这条：内屏横持 860×608dp，竖持即 608×860dp）；
- `EXPANDED && 宽屏双页开关 → 双页`：宽度类别只按宽边算，本身不带方向——900×1000 与
  1000×900 同为 EXPANDED，前者是竖持却同样会进双页（断点是 840dp，
  `WindowSizeClass.WIDTH_DP_EXPANDED_LOWER_BOUND`）。

**处理**：判定加一道方向前置条件——自动模式下**窗口宽 ≥ 高**才允许双页。方向取自
**真实窗口尺寸**（`FoldReaderApp` 的 `LocalConfiguration.screenWidthDp` / `screenHeightDp`，
经 `isPortraitWindow(widthDp, heightDp)` 判定，落到 `FoldableUiState.windowPortrait`），
`resolvePageLayoutMode` 相应增 `windowPortrait: Boolean` 形参并置于判定分支最前。

**不能**改用 `WindowSizeClass` 的 `minWidthDp` / `minHeightDp`：那两个值是"不超过真实尺寸的最大
断点"（宽 0/600/840/…、高 0/480/900），真实尺寸已被丢弃——阔折叠竖持 608×860dp 会落成 600×480，
反倒判成横向（这正是首版实现的错误）。

半折（HALF_OPENED）原先就恒单页，"强制单页 / 强制双页"语义不变。

横竖切换走既有链路：窗口尺寸变化 → `FoldableUiState` 重建 → 重组提交流程 →
`setViewports(dual = …)` → 以锚点重分页，单页 ↔ 双页无感切换，位置不丢。

## 附录：v2.0 漫画阅读模式

**目标**：把「一个目录 / 一个压缩包」读成一本书，支持常见漫画容器与主要阅读功能，
与电子书共用同一个书架。

### 一、来源与存储策略

**只登记元数据，不复制内容**（`books` 表新增 `COMIC` 格式 + `comicContainer` /
`comicPageCount` / `comicLocalPath` 三列）。源被移动或删除后打开会明确报错，
用户可选择「复制到本地」把内容解包进 `filesDir/comics/local/<hash>/` 脱离外部授权。

| 容器 | 扩展名 | 读取方式 | 需要解压缓存 |
|---|---|---|---|
| ZIP | `.cbz` / `.zip` | commons-compress `ZipFile` + `SeekableByteChannel`，读中央目录按条目取图 | 否 |
| 7z | `.cb7` / `.7z` | 条目流只对 `getNextEntry()` 的当前条目有效，**顺序解压一次** | 是 |
| TAR | `.cbt` / `.tar` | 无中央目录，顺序解压一次 | 是 |
| RAR | `.cbr` / `.rar` | junrar 只能顺序读，解压一次 | 是 |
| 图片目录 | 目录 | SAF 列子项，逐页按需读 | 否 |

**为什么只有 zip 走随机访问**：`SevenZFile.getEntries()` 返回的只是元数据副本
（文档明确说明其条目不能用于读内容），7z 的随机访问必须自己顺序扫到目标条目，
对固实压缩还不如一次解压；tar/rar 同理。所以「顺序容器首开解压一次」是这三类的共同解法，
产物落在 `filesDir/comics/cache/<hash>/pages/`（可回收）。

依赖：`commons-compress 1.28` + `org.tukaani:xz`（LZMA 解码，commons-compress 只把它声明为
可选）+ `junrar`（UnRAR License，只做解压）。release 下 R8 需要 `-dontwarn` 几个可选后端
（zstd / brotli / xz / junrar / slf4j），规则已写入 `proguard-rules.pro`。

### 二、页序与配对

页码错一位整本就错位，所以两件事都固定成纯函数并单独配单测：

- **页序**（`ComicPageOrdering`）：逐路径段自然序比较，段内数字串按数值比
  （`1.jpg < 2.jpg < 10.jpg`）；过滤 `__MACOSX/`、`._*`、`Thumbs.db` 等噪音条目。
- **跨页配对**（`ComicSpreadIndex`）：双页模式下「哪几页并排」不是 `(2k, 2k+1)`——
  封面单独成页、横向跨页大图独占整宽都会让之后的配对整体错位。配对一次性预计算成索引
  （页 → 跨页序号），进度恢复、缩略图跳转、翻页步长全部查表，不再各自推算。

「横向宽图」需要每页的宽高比，靠**后台探测图片头**（几十 KB，不解码像素）拿到：
`ComicReaderViewModel.probePageSizes` 在开书后异步扫一遍（超过 2000 页放弃），
结果同时供滚动模式的条目高度使用——高度稳定才不会在滚动中跳位。

### 三、阅读功能

| 功能 | 实现要点 |
|---|---|
| 单页 / 双页 | 复用 `resolvePageLayoutMode` / `dualSplit` / `contentRectFor`；双页沿用书脊与铰链避让 |
| RTL（日漫） | 只作用于**带方向的输入**，且必须同一口径：点击热区左右语义（点左=下一页）、同对页内的左右归属（低序号在右）、横滑（右滑=下一页）、滚轮（上滚=下一页）、翻页动画的滑入侧（下一页从**左**滑入）。口诀：点击是「往前进方向点」，横滑是「把内容往哪边拖」（与下一页相反），动画永远跟横滑同向。音量键 / 媒体键 / PageUp-Down / 空格本身就写着「上一页 / 下一页」，保持语义不镜像。翻译收在 `ComicLogic` 的 `comicTapForward` / `comicSwipeForward` / `comicWheelForward` / `comicSlideFromRight` 并有单测——单独漏翻任何一处都会让同一动作在不同输入下方向相反 |
| 纵向连续滚动 | `LazyColumn` + 按真实宽高比定条目高度；页间距 0 即无缝条漫；滚动位置反写进度 |
| 缩放与平移 | 双指缩放（以中点为锚）+ 拖动平移 + 四种适应模式；单指拖动仅在内容溢出时接管，否则放过给翻页手势 |
| 缩略图跳转 | 底部网格，三级来源（内存 → 磁盘 JPEG → 容器读页），打开时滚到当前页 |
| 进度 / 计时 | 位置按**页序号**存 `reading_progress.comicPage`（不与文本的字符偏移混用同一列） |

**关于双击放大**：没有做。双击要与「点按翻页」共存就必须给 `detectTapGestures` 挂
`onDoubleTap`，而那样每次点按翻页都要先等一个双击超时（约 300ms）才响应——为了翻页跟手，
改为「双指缩放 + 适应模式」覆盖放大需求（`FIT_WIDTH` 是扫描版漫画最实用的一档）。

### 四、与既有链路的关系

- **路由分流**：`ReaderHost` 按 `book.format` 选阅读器。文本阅读器对 `COMIC` 直接报错
  （防御性断言），不让压缩包走文本索引那条路。
- **目录扫描**（`BatchImportUseCase.enumerateTree`）：目录树里「直接含 ≥3 张图片」的目录按
  一本漫画收集且不再下探——一卷一个目录是最常见的存法；门槛而不是「有图就算」，
  是为了不把文字书库里的零散插图目录当成一本书。
- **后台预热**：`BookPrewarmQueue` 增加漫画分支，把顺序容器的解压挪到导入后的空闲时间，
  与 EPUB/FB2 的导入后压平同一套思路。页数在导入时未知的（rar/tar/7z）书架显示「待解析」。
- **缓存回收**：`ComicExtractionStore.sweep` 只清 `cache/`，用户显式选择的 `local/` 不动。

### 五、已知取舍

1. 「以漫画打开一个目录」会递归合并子目录（`ComicFolderScan`，深度 2），而**导入**时每个叶子
   目录各算一本。两个入口语义不同：前者是"读这一个"，后者是"建书库"。
2. 目录漫画的内容哈希由 Uri 派生（目录没有单一文件可采样），因此目录之间不做内容去重，
   去重只按 Uri；容器文件仍按采样哈希去重。
3. 超过 2000 页不再探测宽高比，跨页识别与滚动模式在该规模下退化为固定配对 / 占位高度。

## 附录：v2.1 PDF 阅读模式

**目标**：PDF 既能按页渲染阅读（扫描件、版式稿），文本型 PDF 还能把正文提取出来当电子书读
（可重排、可调字号、能全文搜索、有书签与统计）；加密文档可输密码；文档自带目录可跳页。

### 一、两条渲染路径，各司其职

| 用途 | 用什么 | 为什么 |
|---|---|---|
| **页面渲染** | `androidx.pdf` 的沙箱文档服务 | 真正的解析与光栅化发生在**独立进程**（`isolatedProcess` 的 bound service，内部是平台 `PdfRenderer`）。PDF 是攻击面最大的消费级格式之一，而我们打开的是用户从外部给的文件，这层隔离不是可选项 |
| **元数据 / 目录 / 封面 / 正文** | PdfBox-Android | 一次性解析工作，不需要渲染服务那套隔离；而且目录树、`DocumentInformation`、`AccessPermission` 这些平台 API 根本拿不到 |

依赖：`androidx.pdf:pdf-core` + `pdf-document-service`（1.0.0-beta01，`@ExperimentalPdfApi`，
版本锁死）+ `pdfbox-android 2.0.27.0`。**不要排除 `pdf-viewer`**：它不只是成品 UI，
`pdf-document-service` 的服务端代码（`PdfDocumentRemoteImpl.getPageDimensions`）引用了
它里面的 `androidx.pdf.models.Dimensions`——排掉之后独立进程会在该调用上
`NoClassDefFoundError` 直接 FATAL，binder 一死整个文档作废，而现场只看得到 `DeadObjectException`。

### 二、渲染约束（都踩过）

- `BitmapSource` **一次只能开一页**，所以渲染必须串行（`PdfPagedSource` 用 Mutex 串起来）；
  预取是并发的，不锁会随机拿不到图。
- 出图是 `ARGB_8888`（平台 `PdfRenderer` 的限制），比漫画那条路的 `RGB_565` 占一倍内存。
  因为复用漫画的页式阅读器，内存预算按同一套 `MAX_IMAGE_BYTES` 算，识别为大图的场景要留意。
- 独立进程会**重跑 `Application.onCreate`**：`isIsolatedProcess()` 早退必须保持在所有初始化之前，
  否则日志初始化碰 SharedPreferences 会直接杀进程，表现为 `openDocument` 永久挂起（没有异常）。
- 页面尺寸用 `getPageInfos(全范围)` **一次批量**取（`PageInfo.width/height` 单位是点），
  逐页发 IPC 在几百页的文档上会明显变慢。

### 三、页式阅读器通用化

漫画与 PDF 共用同一个页式阅读器，接缝只有一个：

```
PagedImageSource      // 页数 / 批量宽高比 / 出图 / 缩略图
├── ComicPagedSource  // 容器 → 解码（含 GIF/动态 WebP 的动画判定）
└── PdfPagedSource    // 沙箱文档 → 渲染（串行、ARGB_8888）
```

`PagedReaderFeatures` 描述格式差异，菜单据此隐藏无意义的开关：PDF 没有左右阅读方向，
页面自带留白也不适合「无缝拼接」，跨页配对同样少见。**「双页」不受影响**——那是折叠屏的
版式选择，PDF 一样用得上（只是不做封面单独/宽图独占）。

### 四、文本模式：借 TXT 管线

文本型 PDF 的正文由 PdfBox `PDFTextStripper` 按页抽出，压平成
`convertedDir/<contentHash>.txt` + `.toc` / `.pages` sidecar，之后**完全复用 TXT 管线**：
分页、全文搜索、书签、划线、阅读统计一行都不用重写。

- **一次遍历拿全文与页边界**：`pageEnd` 设哨兵串，而不是逐页调用 `getText`（后者是 O(页数)
  次文档遍历）。
- **扫描件不产出压平产物**：平均每页字符数低于阈值就判定为扫描件，压平步骤
  **安静返回 null**（不是报错、也不写空文件）。否则书架上会多一本"能打开但全是空白"的假电子书。
  界面据此显示「这是扫描件，暂不支持取字」，而不是摆一个点了没反应的按钮。
- **目录两套锚点并存**：压平时我们知道每页正文的起始字符偏移，所以同一个目录项同时写
  `pageIndex`（页式用）与 `charStart/charEnd`（文本用）。这是压平产物的**实测**对应关系，
  不是把页序号当字符偏移用；两套坐标各自的语义没有被破坏。
- **阅读位置互不换算**：两种模式各自记自己的位置（页序号 ↔ 字符偏移不互转），切回去还是
  各自上次停的地方。模式偏好存 `book_prefs.pdfReadingMode`，`null` = 由文档决定
  （抽得出正文就文本模式）。

### 五、导入与预热

导入**只登记**（哈希去重 + 写库 + 入预热队列），不解析：批量导入几十个 PDF 时不会卡在解析上，
页数先留空、书架显示「待解析」。后台预热分两趟：

1. 元数据 / 目录 / 封面 / 页数（PdfBox 一趟）→ 目录写 `chapters`（此时只有页锚点）；
2. 文本型才抽正文压平 → 目录以**两套锚点**重写一次，`totalChars` 落库。

PdfBox 解析不了不代表读不了（加密、非常规结构），所以第一趟失败会退回「只用沙箱拿页数」：
拿得到就算准备完成，拿不到才让「待解析」角标留着等用户输密码。**密码不落库、不进备份、不写日志**。

### 六、已知取舍

1. **扫描件 OCR 不做**：系统层没有可用的公开 OCR API（Pixel 的取字是 System Intelligence
   内部组件，OEM 的不可靠），`androidx.pdf.ocr.OcrProvider` 只被它自己的 `PdfViewer` 消费，
   自绘路径用不上。这条留待将来"页位图 → 自托管离线 OCR → 带坐标的文本层"。
2. **纸书页码**用「第 N 页」而不是 PDF `PageLabels`（罗马数字前言那类），后者要额外接线，
   价值低。
3. **PdfBox 的 optional `com.gemalto.jp2`（JPEG2000）没有打包**：只影响"页面里嵌 JP2 图"的
   解码，而正文抽取不碰图像；首图恰好是 JP2 时封面渲染失败、回退标题占位封面。
   R8 需要 `-dontwarn com.gemalto.jp2.**`。
4. **`androidx.pdf` 是 beta 且关键 API 标 `@ExperimentalPdfApi`**：版本锁死，留升级窗口。
5. **>250MB 的 PDF 打开与翻页会明显变慢**（官方已知性能问题）。已做**大小预警**：
   打开时取一次文件大小，超过 250MB 在页式菜单里给一句「文件较大，翻页与缩放可能偏慢」。
   只提示、不挡开书——大文件慢是事实，不是错误。

## 附录：v2.2 页内锚点 + 可配中间点击区 + 同系列切换

### 一、中间点击区（可配单击 / 双击）

点击分区由「左 / 中 / 右」三段构成（`tapZoneOf`），中间那段过去硬编码为「开菜单」，
现在是一个**可配置区域**：单击与双击各绑一个 `TapAction`（菜单 / 上下页 / 书签 / 缩放 / 无）。

关键实现约束：**不能给根手势加 `onDoubleTap`**。`detectTapGestures(onDoubleTap = …)` 会让它收到的
每一次单击都等一个双击超时（约 300ms）才派发，加在根手势上会把左右翻页也拖慢。
所以双击被限制在一层**只覆盖「判定为中间区」那块矩形**的点击层里（`MiddleTapLayer`）：
左右翻页区（以及文本阅读器启用时的底边翻页条）都不被覆盖，保持抬手即响应。这顺带解掉了此前"要不要为了双击缩放
牺牲翻页跟手性"的取舍。漫画阅读器不启用底边翻页条（底边随左右热区分区），它的中间区是整高。

阅读器执行不了的动作（文本阅读器的「缩放」）会**整层不挂**（`supportsTapAction`），
所以默认配置下文本阅读器的点击路径完全不变。

### 二、页内锚点（书签 / 高亮 / 选字）

页式格式的书签与高亮存「**页序号 + 归一化页内坐标**」：

- 归一化（0..1）是刻意的。渲染尺寸随适配模式、缩放、窗口与分屏变化，存像素必错位；
  归一化后绘制时乘当前绘制尺寸即可自动跟随。PDF 的"点"与漫画的"像素"两种单位
  也在这一层被抹平。
- 书签可以是**点**，也可以是**框**；一页可有多条（容差 3%，见下）。
- 长按**不动** = 在该点加/删书签，长按**拖动** = 框选（`MIN_SELECTION_SIZE` 区分，
  避免指腹抖动被当成框选）；框选后动作条给「色点高亮 / 下划线 / 书签 / 复制 / 取消」。
- 锚点手势放在**每一页内部**（`ComicPageView`）：那里天然知道页序号、容器尺寸与缩放变换，
  双页模式下不必去算铰链分区，坐标永远是页内坐标。
- 页内选区先按手指画的框亮出来（动作条立刻可用），随后向文档换取**它自己的选区**（见下节）。

### 三、页内选字为什么用文档的选区而不是自己匹配

探针（对 `androidx.pdf` 1.0.0-beta01 的 pdf-core）确认了可用 API：

- `PdfDocument.getSelectionBounds(page, PointF, PointF)` → `PageSelection`
  （含 `PdfPageTextContent` 的**并集矩形与选中文字**）；
- `getPageContent(page)` → 页文本；`searchDocument(q, range)` → 逐页命中；`getPageLinks(page)` → 链接。

原计划是「取回页文本、在本地按矩形吸附」，看到这个 API 后改掉了：阅读顺序、连字、跨栏
只有文档自己知道，交给它更准，而且省掉本地匹配逻辑。

约束与降级：选字是**一次用户动作调一次**（拖框期间不发 IPC）；已确认是扫描件时直接跳过；
拿不到结果就保留原始矩形框——扫描件与漫画本来就只有框选。多行选区取的是**并集框**
（一整块矩形），与"区域是一个框"的数据模型一致。

### 四、同系列前后切换

漫画没有内嵌目录，前后卷只能靠文件名推断。`core/comic/ComicSeriesMatch.kt` 是纯逻辑：

- 主干 = 去扩展名 → 去括号标签 → 全角转半角 → 抹掉卷号 → 非字母数字压成单空格；
- 卷号提取覆盖 `第3卷`/`第三巻`/`v03`/`vol.3`/`ch.5`/`- 09`/`(11)`/`_04`；
- **判据只有「主干相等」，不做相似度匹配**：误判的代价是跳到一本不相干的书，宁可漏；
- 只有一个来源有卷号时，**有卷号的排在前面**（有序卷在前、番外 / SP 在后）。

两个来源：**同目录**（可能尚未导入）与**库内**（同分组或同目录）；同 uri 去重且库内优先
（它带着 bookId，点进去就能打开）。未入库的卷显示「未导入」，点击时**按需导入**再打开——
只导入了第 3 卷时，若只列已入库的书，这个功能就等于没用。

**SAF 的坑**：SAF 没有「取父目录」的 API。`DocumentsContract` 只给 `getDocumentId`，
所以同目录枚举只能从 documentId 反推（`primary:comics/Foo/01.cbz` → `primary:comics/Foo`）。
形如 `1234` 的不透明 id（Downloads 提供方）反推不出来，此时返回空列表——
**宁可不提供这个功能，也不能猜一个可能错误的目标**。

切卷用 `popUpTo(READER){inclusive}` 替换当前阅读页，返回时回书架而不是退回上一卷。

### 五、页式阅读补齐的能力

- **全文搜索**（文本型 PDF）：命中只给「页 + 命中数 + 附近文字」。`PageMatchBounds` 不带文字，
  上下文要按 `textStartIndex` 回取页文本切片（每页一次 IPC，只给前 40 页取）。
- **自动翻页**：间隔模式到点发请求，界面走**正常翻页动画**（与手动翻页同一条路）；
  滚动模式用 `dispatchRawDelta` 按 px/s 同步推进（不必每帧起协程）；
  手动操作后暂停一段时间，沿用文本阅读器的 `AutoPageClock`。
- **跳到指定页**：页数多时进度条点不准（几百页时 1% 就是好几页），给数字输入。
- **外接键盘 / 鼠标**：方向键 / PageUp-Down / 空格 / 媒体键翻页，滚轮翻页。
- **>250MB 大小提示**（见 2.1 六.5）。

### 六、顺带修掉的两个既有缺陷

1. **双模式 PDF 的进度互覆盖**：`reading_progress` 是每本书一行且 upsert 是整行 REPLACE，
   文本模式保存时没带上 `comicPage`，于是「页式读到第 50 页 → 切文本 → 切回」位置就没了。
   改为对称的 `keepPagedAnchor` / `keepTextAnchor`，两个阅读器都走它。
2. **双指缩放的锚点漂移**：原公式漏了「捏合点相对页面中心」这一项，捏合点偏离页面中心时
   缩放不跟手。已抽出 `comicZoomAnchored` 统一双指与双击缩放的锚点数学。

### 七、已知取舍

1. **PDF 内链跳转未做**：需要「根坐标 → 页内坐标」的映射，而页内锚点刻意放在页内部以避开
   这层管道；且链接只影响脚注/交叉引用这类场景，暂不值得为此重做坐标层。
2. **缩放不跨页保持**：本阅读器的缩放是每页重置的设计（换页即复位），临时倍率跨页保留会让
   "这一页为什么是放大的"变得不可预期；适配模式本身是持久化的。
3. **纵向连续（条漫）模式下的锚点手势未做**：页内坐标与屏幕坐标不是一套换算，
   要像文本阅读器那样再维护一份滚动命中逻辑。已有书签与高亮照常显示。
4. **书签去重容差 3%**：页内坐标来自手指落点，要求浮点完全相等等于永远找不到已有书签，
   toggle 会退化成一直新增；容差也不能大，否则会把旁边那条书签吞掉。
5. **高亮只存在应用内**（数据库），本轮**不写回 PDF 文件**：写回需要 `PdfRenderer.write()`
   或平台批注写入，且要处理沙箱进程的导出往返。
