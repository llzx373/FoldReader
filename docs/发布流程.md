# 发布流程

本文说明如何把 FoldReader 发布为一个 GitHub 正式版本。发布由 [`.github/workflows/release.yml`](../.github/workflows/release.yml) 自动完成：打 tag 即打包、签名、创建 Release。

---

## 一、一次性准备

### 1. 生成发布密钥

签名密钥决定了后续所有版本的覆盖升级能力。**一旦丢失，已安装的用户将无法升级到新版本**，只能卸载重装。

```bash
keytool -genkeypair -v \
  -keystore foldreader-release.keystore \
  -storetype PKCS12 \
  -alias foldreader \
  -keyalg RSA -keysize 4096 -validity 10000
```

要点：

- `-validity 10000` 约 27 年，避免密钥在应用生命周期内过期。
- `-alias foldreader` 是密钥别名，之后要填进 GitHub Secret。
- 会依次询问密钥库口令、密钥口令与证书主体信息（姓名/组织/地区）。两项口令建议设成同一个值，省去区分。
- 生成后**请立刻离线备份**（密码管理器 + 异地存储）。这个文件不应只存在于你的开发机上。

### 2. 转成 Base64

CI 通过 GitHub Secrets 传输密钥文件，需要先转成单行 Base64。

**Windows PowerShell**

```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes("foldreader-release.keystore")) | Set-Clipboard
```

**Linux**

```bash
base64 -w0 foldreader-release.keystore > keystore.b64
```

**macOS**

```bash
base64 -i foldreader-release.keystore -o keystore.b64
```

> 转换完成后请删除中间产物（如 `keystore.b64`），它等价于明文密钥。

### 3. 配置 GitHub Secrets

进入仓库 **Settings → Secrets and variables → Actions → New repository secret**，添加 4 个 Secret：

| Secret 名称 | 值 |
| --- | --- |
| `KEYSTORE_BASE64` | 上一步得到的单行 Base64 字符串 |
| `KEYSTORE_PASSWORD` | 密钥库口令 |
| `KEY_ALIAS` | 密钥别名（如 `foldreader`） |
| `KEY_PASSWORD` | 密钥口令 |

四个配齐时使用正式签名。**缺任何一个都会退化为 debug 签名**：流水线会给出醒目告警，并在 Release 说明顶部写明「本版本使用 debug 签名」。

debug 签名只是为了让发布链路在没有密钥时也能先跑通，产物**不可分发给用户**——debug 密钥由构建机即时生成，与本机 debug 包、以及后续用正式密钥签名的包互不兼容，用户从该版本升级时必须先卸载。

> 当前状态：首个 `v1.0.0` 就是以 debug 签名发布的（见 [CHANGELOG.md](../CHANGELOG.md)）。配好上面 4 个 Secret 后，之后的版本会自动切换为正式签名，告警与说明条目也会自动消失。

### 4. 确认本地环境

发布前请先在本地跑通一次，避免把编译错误留到 CI：

```bash
./gradlew :app:testDebugUnitTest
./gradlew :app:assembleRelease
```

本地没有密钥时会回退 debug 签名；这只是让贡献者能验证 release 包的体积与性能，不代表可以这样发布。

## 二、版本号规则

`versionName` 就是 tag 去掉前缀 `v`，`versionCode` 由版本号推导：

```
versionCode = major × 10000 + minor × 100 + patch
```

| tag | versionName | versionCode |
| --- | --- | --- |
| `v1.0.0` | `1.0.0` | `10000` |
| `v1.2.3` | `1.2.3` | `10203` |
| `v1.1.0-rc1` | `1.1.0-rc1` | `10100`（预发布后缀不参与计算） |

约束：

- **`versionCode` 只能递增。** 用户设备的升级判定只看 `versionCode`，回退版本号会导致无法覆盖安装。
- 带 `-` 后缀的 tag（如 `v1.1.0-rc1`）会被自动标记为 **Pre-release**，不会占用「Latest release」位置。
- 约束上限：`minor` 与 `patch` 均需小于 100，即 `v1.99.99` 是安全上限。

### 开发期版本号（铁则）

**开发期间不主动递增版本号。** 目标版本固定在 `gradle.properties` 的默认值（当前 `1.1.0`），
本地与测试包一律用 `1.1.0-<开发序号>`（序号从 1 起递增）作为 `versionName`，
`versionCode` 保持该目标版本的基础值（`1.1.0` → `10100`）：

```bash
./gradlew :app:assembleRelease -PfoldReader.versionCode=10100 -PfoldReader.versionName=1.1.0-1
```

产物按既有习惯命名 `FoldReader-1.1.0-<序号>-clean.apk`，序号取已有产物里最大的 +1。

- **只有确定要发布的那一个提交**才用不带后缀的 `1.1.0`，由发布流水线用 tag 注入。
- 目标版本号只在**里程碑**推进时改（`1.1.0` 之后的下一个里程碑才是 `1.2.0`），
  不要为每次小迭代各占一个正式版本号。
- 理由：`1.0.1`、`1.0.2`… 这种「一次小迭代一个正式版本号」会消耗得比功能推进快得多，
  而用户看到的每一个正式版本号都应当对应一个有意义的里程碑。

## 三、发布一个版本

1. **更新 `CHANGELOG.md`**：把 `## [Unreleased]` 的内容整理成 `## [x.y.z] - YYYY-MM-DD`，并补上版本比较链接。
2. **确认 `main` 上的 CI 是绿的**，且 `app/build.gradle.kts` 中的 `foldReader.versionCode` / `foldReader.versionName` 默认值无需改动（发布时会被 tag 覆盖）。
3. **提交并推送**。
4. **打 tag 并推送**：

   ```bash
   git tag v1.0.0
   git push origin v1.0.0
   ```

5. 到仓库 **Actions → Release** 观察流水线。它会依次：解析版本号 → 校验签名密钥 → 写入签名配置 → 构建 release APK 与 AAB → 用 `apksigner` 校验证书 → 创建 GitHub Release。
6. 在 **Releases** 页面核对产物：
   - `FoldReader-<版本>.apk` —— 给用户安装的包
   - `FoldReader-<版本>.aab` —— 留给未来上架应用商店
   - `FoldReader-<版本>-mapping.txt` —— R8 混淆映射表，用于还原用户上报的崩溃堆栈

### 手动发布

在 **Actions → Release → Run workflow** 中选择分支并填写版本号（如 `1.2.0`）。流水线会在该分支最新提交上创建 `v1.2.0` tag 并发布。

与推 tag 的区别只在于 tag 由谁创建。常规发布仍建议手动打 tag——tag 与提交的对应关系更直观，也不会因为选错分支而把 Release 挂到预料之外的提交上。

## 四、验证发布结果

```bash
# 确认签名证书是正式密钥而不是 debug 密钥
apksigner verify --print-certs FoldReader-1.0.0.apk
```

输出中的 `Signer #1 certificate DN` 应为你生成密钥时填写的主体信息。若显示的是 `CN=Android Debug`，说明这次走的是 debug 签名（未配置 Secrets），产物不可分发。

之后在真机上验证：全新安装一次、覆盖安装一次。

## 五、排错

| 现象 | 原因与处理 |
| --- | --- |
| 流水线日志出现「未配置完整的签名 Secrets」告警 | 4 个 Secrets 未配齐或名字拼错，见第一节第 3 步；此时产物是 debug 签名 |
| 已配 Secrets，`apksigner` 仍报 debug 证书 | 流水线会直接失败。`key.properties` 未生效——检查 Secret 值是否被换行或空格污染（Base64 必须是单行） |
| 安装时报 `INSTALL_FAILED_UPDATE_INCOMPATIBLE` | 新包签名与设备上已装的包不一致。换了密钥、或设备上装的是 debug 签名包（含首个 `v1.0.0`）时都会这样。卸载后重装 |
| 安装时报版本降级 | `versionCode` 比已装版本小，检查 tag 的版本号是否递增 |
| Release 说明里没有提交列表 | `checkout` 的 `fetch-depth` 被改成浅克隆，`git log` 拿不到历史 |
| `sdkmanager --install` 找不到包 | CI 上的 Android SDK 包名与本地不一致，改动点集中在 `.github/actions/setup-build/action.yml` 的「Install Android SDK components」步骤 |
| gradle 构建报 `key.properties` 相关错误 | Secrets 中的口令有误，或 Base64 解码后的文件不是合法密钥库；CI 会把密钥写到 `$RUNNER_TEMP/release.keystore` |

## 六、CI 流水线（非发布）

[`.github/workflows/ci.yml`](../.github/workflows/ci.yml) 在 push 到 `main` 与所有 PR 上运行，包含单元测试、Lint 与 debug 包构建。它**不使用任何签名密钥**，因此 fork 出来的 PR 也能正常跑。
