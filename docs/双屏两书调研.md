# 双屏同开两本书调研（M33）

日期：2026-10-09 · 结论：**不做**（应用内双书实例），理由与备选路径归档如下。

## 需求

折叠屏展开后左右半屏各开一本书（对照阅读 / 抄注场景）。候选技术路线：
activity embedding（androidx.window.embedding）、系统 multi-window、应用内单窗口双栏双书。

## 现状约束（决定成本的关键事实）

- **单 Activity + NavHost**：`MainActivity`（`launchMode="singleTask"`，全部 configChanges 自理，
  `resizeableActivity="true"`），导航与进书转场都在单个 Compose NavHost 里。
- **进程级单态**（`FoldReaderApplication.container` / AppContainer）：
  - `activeReaderBookId`——单值 StateFlow，编码切换、TTS 路由、词典卡片等阅读期自治组件都靠它定位「当前书」；
  - TTS `ReaderTtsController`、三个前台服务翻译/摘要队列、词典库、下载中的模型管理——全都按「一个活跃读者」设计。
- **ReaderViewModel 按 `reader-$bookId` 键**：同一 NavHost 内并存两个阅读页没有结构性障碍，
  但共享单态（见上）与导航转场（进书共享元素动画、返回手势）都假定单读者。

## 路线评估

### A. activity embedding（androidx.window.embedding）

把任务窗口分成两个 Activity 容器，左右各跑一个阅读 Activity。

- 需要把阅读器从 NavHost 路由拆成独立 Activity（或第二个占位 Activity + 独立的局部分支），
  进书/返回/深链/「打开方式」intent 路由全部要按双容器重排；
- 两个 Activity 同进程 → 上面的单态全部变成竞态（`activeReaderBookId` 只有一个值，
  两个阅读器互相覆盖；TTS 永远只有一个音源，归属判定要重做）；
- androidx.window.embedding 分屏主要由大屏（平板/展开态内屏）系统窗口驱动，
  双屏/半屏物理分区的表现在各 OEM 间不一致，无法保证「左屏一本书右屏一本书」恰好落在物理屏上；
- 依赖与规则配置本身不重，但**架构改造成本是一次阅读器多实例化重构**，风险面覆盖阅读/TTS/翻译/词典。

### B. 系统 multi-window（分屏 / 自由窗口）

- 今天已可用：`resizeableActivity="true"` + configChanges 自理，与任意其他应用分屏零成本；
- 同应用双实例取决于 OEM（「应用双开分屏」非平台能力）；即便系统放行，
  第二实例与第一实例同进程共享 AppContainer 单态，同样踩 `activeReaderBookId` 竞态——
  这是**现状已存在**的边界，不是本路线新增的问题，但要把「双开同应用」做成正式能力仍需解单态；
- 收益只是「和别的应用并排」，不满足「同应用两本书」。

### C. 应用内单窗口双栏双书（一个 Activity，内屏左右各嵌一个阅读页）

- 不动 Activity 结构，两个 `ReaderViewModel`（键不同）并排即可成立；
- 但阅读器 UI 假定独占窗口：菜单/对话框/选择层/亮度手势/自动翻页/TTS 归属全部要按「左右实例」参数化，
  工作量与 A 相当，且导航转场、共享元素进书动画在双栏下语义不明；
- 若未来真要做双书，**这条路反而比 activity embedding 便宜**（不碰 intent/任务模型），
  建议届时从这里重启评估。

## 结论

不做。理由：

1. 三条路线的公共硬成本都是**阅读器多实例化**（`activeReaderBookId`、TTS、前台服务队列等
   进程单态解耦），这不是一个里程碑能安全吞下的改造；
2. 「展开态边读边查」的核心诉求已由 M33 桌面模式面板（上半屏正文 + 下半屏目录/批注/术语表）
   与既有双页对照（M20）覆盖；
3. 对照阅读的真实频次低，系统分屏（路线 B）已为跨应用对照兜底。

重启条件：出现稳定用户诉求时，按路线 C 重启评估；第一步是把 `activeReaderBookId`
从单值改为「每阅读实例一份」的注入式上下文。
